# 設計: 有限選択肢に確率で答える音声コマンド

## 0. 何を解くのか

道路カメラの監視員は電話や別作業をしながら「船橋南1上りを出して」「もっと右」「引いて」と口で指示したい。
要件は 3 つ。

1. **確実さ**: 数万台から 1 台を選ぶ。聞き間違いは許されないが、確信が無いときは「〜ですか?」と聞き返してよい。
2. **ウェイクワード無し**: 電話の相手への「はい」「少々お待ちください」をコマンドとして拾ってはいけない。
3. **汎用性**: カメラ以外のシステム操作にも同じ仕組みを使いたい。地名などの選択肢は整理して持ち、担当範囲で絞れること。

## 1. 中心となる考え方 (typesafe / Decision Model からの持ち込み)

生成 (文章を書かせる) ではなく、**有限の選択肢へ確率で直接答えさせる**。
Decision Model では LLM/VLM の出力層を選択肢の上の分布に置き換えたが、音声でも同じことができる:

    音声 -> kana-whisper encoder (1 回)
         -> 自由認識 (greedy) でカナ列 s_free            … 「何と聞こえたか」
         -> 状態に応じたコマンド集合から近い候補を K 個   … 「今この状態で言えること」に絞る
         -> K 候補 + 自由認識をまとめて教師強制で採点     … log p(候補カナ | 音声)
         -> 校正 (温度 T、該当なしバイアス β) -> 確率     … 「該当なし」も選択肢の 1 つ
         -> 3 段閾値 (実行 / 確認 / 棄却) × 意図の危険度

ポイントは 3 つ。

- **「聞こえたカナ」と「候補」の比較を、文字列の近さではなく音声に対する尤度で行う。**
  「ナシラノ」と聞こえても、音声に対しては「ナラシノインター」の尤度がほぼ 1.0 になる (実測)。
- **該当なしを明示的な選択肢にする。** 自由認識の尤度 − β を「どの候補でもない」の logit として並べる。
  文法外の発話は候補の尤度が 20〜50 nats 落ちるので、そこに確率が集まる。閾値で切るより頑健で、確率として出る。
- **同じ意味の表層形は確率を足す。** 「船橋南1上り」「船橋南1上りを表示」「〜出して」は別の仮説だが、
  意味 (意図 + スロット) が同じなので合算してから判断する。

## 2. 状態遷移とコマンド集合

ウェイクワードの代わりに、システムの状態が受理する発話を決める (state.py + grammar.py)。

| 状態 | 受理する意図 | 仮説数 (首都国道 100 台) |
|---|---|---|
| WALL (一覧) | カメラ名 (拡大表示)、ヘルプ | 1,623 |
| FOCUS (拡大中) | 右/左/上/下、寄る/引く、ホーム、戻る、別カメラ、プリセット保存 | 1,770 |
| CONFIRM (確認待ち) | はい / いいえ | 10 |

確認待ちでは選択肢が 10 表層形しかないので、雑音 SNR 10dB でも 100% (18/18) で当たる。
「危険な操作ほど選択肢を減らして確実に取る」という構造が、状態機械から自然に出る。
確認待ちは 8 秒で自動キャンセルし、電話相手への「はい」を後から拾わないようにしている。

テンプレートは `{camera}[を](表示|出して|見せて)` の記法で書き、`[ ]` 省略可、`( | )` 択一、
`{slot}` は lexicon の kind ごとに全実体へ展開される。意図には `risk` (low/medium/high) が付き、
high は確信度に関わらず必ず確認になる。

## 3. 選択肢の管理 (lexicon.py)

- Entity = 指せるもの 1 個。表示名、複数の読み (ASR 形カナ)、別名、属性 (整備局/事務所/県/路線/方向...)。
  別名の読みが範囲内で複数の実体に当たる (「船橋南」= 上り/下り) ときは compile が落とす。単独では選べないため。
  将来は「上りですか下りですか」と聞き返す曖昧性解消の仮説にするのが筋。
- Scope = 担当範囲。属性フィルタの AND + 個別追加 + 個別除外。「首都国道事務所の国道 14 号」のように作る。
  範囲ごとに事前学習の結果 (校正値・精度・混同対) を持つ。
- 読みの優先順: 人手 > 事前学習で採れた実現読み > 郵便番号データ (KEN_ALL) > G2P (pyopenjtalk)。
- すべての読みは kana-whisper の書き方 (ASR 形) に正規化する: 長音は「ー」、ヲ→オ、ヂ→ジ、句読点除去。
  さらに イ段+イ / ア段+ア の長音揺れは表層バリアントとして両方を仮説に入れる。

## 4. 事前学習 (synth.py) — 担当範囲を登録したときに走る

TTS (Irodori) で範囲内の各カメラ名を複数の声で合成し、認識器を通す。得られるもの:

1. **校正値 (T, β0, β1, γ)**: 候補と自由認識の対数尤度から NLL 最小化で求める。これが最も効く。
   校正サンプルは実行時と同じ analyze() 経路で採点し (埋め込み採点込み)、カメラ名だけでなく
   PTZ・はい/いいえ・文法外の発話も他状態のコマンド集合に対して採る (短い候補に緩くならないように)。
   未校正では雑音下で 82% だった正解率が、校正後は argmax 99% / ECE 0.01 前後になる (docs/evaluation.md)。
2. **実現読み**: ASR が実際に書く読みを採って登録する。TTS には**読みカナを渡す** (表示名を渡すと TTS の誤読を測ってしまう)。
3. **表示名の読み照合**: 表示名 (漢字) で合成した結果が登録読みと大きく違えば「読み要確認」を警告する。
   「谷津」を G2P も TTS も「タニツ/タニズ」と読む、のような固有名詞の誤読が可視化される。
4. **混同対**: 範囲内で取り違えやすいカメラの組。名付けや路線番号の付加で解消できる。
   同名で上り/下りだけ違う組 (船戸2上り/下り) は雑音下で入れ替わりやすいことがここで見える。
5. **文法外の棄却率**: 電話応対の定型句を合成し、該当なしに倒れることを確認する。

雑音付加 (ピンクノイズ SNR 5〜20dB、別発話の重ね合わせ −10dB) を混ぜ、実運用に近い条件で校正する。

## 5. 判断ポリシー (engine.py)

| 危険度 | 実行 | 確認 | 棄却 |
|---|---|---|---|
| low (表示・PTZ) | p ≥ 0.85 | 0.40 ≤ p < 0.85 | p < 0.40 |
| medium | p ≥ 0.95 | 0.40 ≤ p < 0.95 | p < 0.40 |
| high (プリセット保存など) | — | p ≥ 0.40 | p < 0.40 |

該当なしが最尤なら「システム宛でない」として何もしない (UI には薄く表示)。

## 6. 遅延

RTX PRO 6000 (fp16)、首都国道 100 台、発話 2〜3 秒:
encoder 15ms + 自由認識 26ms + 絞り込み 0.5ms + 採点 7ms = **合計 50ms (p95 60ms)**。
全国 2,932 台 (13 万仮説) でも絞り込み 20ms が増えるだけで 75ms 前後。VAD の終話判定 450ms が支配項。

## 7. 汎用化の道筋

- 別システム: Intent の一覧と StateDef の一覧を差し替えるだけ。lexicon の kind を増やせば「{route}」「{preset}」のような複数スロットも同じ仕組みで展開される。
- 選択肢が大きい (10 万件超) 場合: 絞り込みを文字 Levenshtein から音節 n-gram 転置索引に替える (rapidfuzz cdist は 11 万件で 15ms なので当面は不要)。
- 実現読みの学習を進めると、範囲固有の LoRA を kana-whisper に当てる選択肢もある (現状は校正だけで 99.5% なので未着手)。
- 実機: CameraApp._execute の PTZ 更新を ONVIF/独自 API 呼び出しに替える。状態機械と認識は変えなくてよい。

## 8. 限界と注意

- 評価は合成音声 (Irodori TTS) に雑音を足したもの。実マイク・実オフィスの音での精度は未検証。
  ブラウザ UI にマイク入力があるので、実測を貯めて再校正するのが次の一歩。
- kana-whisper は雑音下で「崩れた自由認識に過信」する (lp ≈ −0.15 で誤った読みを出す)。
  そのため許容量は候補長に比例させ (β1 ≈ 1.8 nats/トークン)、文法外との分離は自由認識との尤度差 (40 nats 級) で取っている。
  発話中に別の声が重なる (babble) 条件が最も苦手で、埋め込み採点と校正で救うが、確認に回る割合は多い。
- **重なった発話に弱い**: 別の声を −12dB で重ねると kana-whisper は背景側の語を混ぜて出力し、−18dB でも
  一部で背景が勝つ (オフライン再現: 「ツダヌマイチノボリ」+ 背景「ヒヨシクライチノボリ」−12dB → ヒヨシクライチノボリヒヨシク)。
  TTS の清潔な音声どうしを重ねる条件は現実より厳しい面もあるが、電話のスピーカー音や隣席の声が
  マイクに入る監視室では起こりうる。埋め込み採点 (前景の語が自由認識に残っていれば救える) と
  確認段で緩和し、根本的には話者分離かマイクの指向性で対処する。
- 確認状態で電話相手に言った「はい」は区別できない。タイムアウト (8 秒) と、確認を要する操作を減らす運用で緩和する。
  自分宛判定ヘッド (Aunvox の addressee head) を前段に置くのが本筋。
