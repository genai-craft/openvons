# 「文章を書かない AI」は本当に速くて賢いのか — System One / Jev 再現実験の読み方

対象読者: LLM を API として使ったことはあるが、モデルの中身や学習はやったことがないエンジニア。
この記事は [benchmark.md](benchmark.md) の数字を、背景と意味から説明し直したものです。

---

## 1. そもそも何を作ろうとしたのか

ChatGPT のような LLM は「作文」で答えます。「この問い合わせは配送部門の担当か?」と聞いても、
内部では**次の単語を 1 つずつ選ぶ**という作業を何十回も繰り返して
「はい、この問い合わせは配送に関する内容ですので…」という文章を作り、こちらはそれをパースして使います。

でも業務システムが本当に欲しいのは、たいていこれだけです。

```
配送 91% / 請求 2% / 返品 5% / その他 2%
緊急対応が必要: 12%
深刻度: 軽度 (期待値 1.1)
```

TypeSafe AI の System One / Jev は、この「マークシートだけ返す AI」を製品にしています。
今回の実験は、その性質を公開情報だけで再現して「本当に普通の LLM より速くて賢くて信頼できるのか」を数字で確かめるものでした。

たとえるなら、LLM は**小論文を書かせて採点者が答えを読み取る**方式、Decision Model は**選択肢を読んでマークシートを塗る**方式です。
読解力にあたる部分 (Transformer 本体) は同じものを使い、答え方だけを変えます。

### 中身の話を 1 段だけ

LLM は大きく 2 段構成です。

1. **backbone**: 文章を読んで、各位置の意味を数千次元のベクトルにする本体。パラメータの 99% はここ。
2. **LM head**: そのベクトルを「次の単語は何か」の確率 (語彙 15 万個ぶん) に変換する最後の 1 層。

Decision Model は 2 を捨てて、代わりに「**選択肢ごとの点数**を出す小さな層」を付けます。
今回使った方式では、プロンプトの中に選択肢を並べて書いておき、

- 各選択肢の行の最後の位置のベクトル = **その選択肢を表すベクトル**
- 質問の最後 (`Decision:`) の位置のベクトル = **「で、どれ?」という問い合わせベクトル**

の 2 つを内積で突き合わせて点数にします。あとは softmax すれば確率です。
語彙 15 万個ではなく選択肢 2〜255 個ぶんしか出さないので、**壊れた JSON は原理的に出てきません**。

この作りの副産物として、選択肢が毎回違っても動きます。選択肢の「位置」ではなく「説明文の意味」を見ているからです。

---

## 2. どこで役に立つのか

- **問い合わせの振り分け**: 部署・緊急度・感情を一度に判定し、確信度が高いものだけ自動処理する
- **エージェントのツール選択**: 「検索 / DB 参照 / メール送信 / 何もしない」を毎ターン LLM に長考させずに決める
- **モデレーション**: spam / fraud / abuse を確率付きで判定し、しきい値で人間レビューに回す
- **IoT・見守り**: カメラやセンサーの状態から「転倒 91%」のような判断だけ出す (文章は要らない)

共通するのは「**答えの候補が有限個で、確率が欲しくて、大量に高速に処理したい**」こと。
そして確率が本物なら「0.9 以上は自動実行、それ以下は人間か LLM へ」という運用設計ができます。
これが効くと、LLM の呼び出し回数もコストも桁で変わります。

## 3. 実験でやったこと

1. 同じ API `POST /v1/decision` の裏に「普通の LLM (Qwen3-4B と 27B、vLLM 経由)」と「Decision Model」の両方を置いて、条件を揃えて比較した
2. Decision Model は Qwen の LM head を外し、上で説明した選択肢スコアリング層を付けたもの
3. 公開データ 5 種 (意図分類 18/60 クラス、不快ツイート判定、レビューの星 1〜5、ツール選択) で精度・確率の信頼性・速度を測った
4. 大きい LLM を先生にした蒸留、質問を 16 個まとめて投げる高速化、確率の補正 (calibration) も試した

比較相手をわざと強くした点が重要です。LLM 側は **vLLM + 選択肢に強制する機能 (guided choice) + 出力 1 トークンだけ**という、
実務でやりうる最速設定にしてあります。「LLM に JSON を長々と書かせて遅い」という不公平な比較を避けるためです。

## 4. 何がすごかったか

### (a) 8 秒の学習で、6 億パラメータが 270 億パラメータを上回った

意図分類 (18 クラス、英語) のテスト 2974 件での正答率です。

| | 正答率 |
|---|---|
| Qwen3.8-27B にそのまま聞く | 87.5% |
| Qwen3-4B にそのまま聞く | 82.3% |
| **Qwen3-0.6B 凍結 + 追加した層だけ学習** | **88.1%** |
| Qwen3-4B 凍結 + 追加した層だけ学習 | 91.6% |
| Qwen3-4B + LoRA (本体も少しだけ学習) | 93.3% |

3 行目がこの実験で一番の驚きです。0.6B の**本体は一切いじっていません**。
本体に 1 万件のデータを 1 回通してベクトルを取り出しておき (これが 35 秒)、
その後は小さな層だけを **8 秒**学習させただけ。それで 45 倍大きいモデルのゼロショットを超えました。

意味するところは「読解力はもう十分ある。足りないのは**答え方の訓練**だけだった」。
0.6B でも「wake me up at five」が目覚ましの話だということは理解できていて、
18 個の選択肢のどれに対応するかを教わっていなかっただけ、ということです。

### (b) 質問を 8 個に増やしても、1 個のときの 1.5 倍の時間で済む

同じ問い合わせ文に「配送か? 緊急か? 怒っているか? …」と複数質問するときの応答時間 (p50、4B モデル)。

| 質問数 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| LLM に JSON でまとめて答えさせる | 65 ms | 114 ms | 254 ms | 508 ms | 895 ms |
| Decision Model・素朴に 1 問ずつ | 15 ms | 30 ms | 59 ms | 119 ms | 239 ms |
| **Decision Model・共有 forward** | **15 ms** | **16 ms** | **17 ms** | **23 ms** | **32 ms** |

仕組みは「状態 (問い合わせ文) の読み込みを 1 回だけ行い、質問同士は互いを見ないように attention を区切る」というもの
(block-diagonal attention)。1 回の forward で 16 問ぶんの答えが同時に出ます。
質問が増えてもコストがほぼ増えないので、「とりあえず 20 項目チェックする」という設計が現実的になります。

### (c) 「80% と言ったら本当に 80% 当たる」確率になった

ここが一番地味で、一番実務的に効くところです。確率の信頼性は **ECE** という指標で測ります
(「自信 90% と言った集団の実際の正答率」とのズレの平均。0 が理想、0.05 以下なら実用圏)。

Qwen3-4B にそのまま聞いたときの実測がこれです。

> テスト 2974 件のうち **98% が「自信 0.9 以上」**。その平均自信は **99.9%**。
> ところが実際の正答率は **83%**。

ほぼ全部に「確実です」と言いながら 6 件に 1 件間違える。これでは確率をしきい値に使えません (ECE 0.17)。
学習済みの Decision Model (0.6B) は同じテストでこうなります。

> 自信 0.9 以上は全体の **73%** に絞られ、その集団の実際の正答率は **97.8%**。ECE 0.016。

「わからないときはわからないと言う」が成立しています。さらに温度補正 (後述) をかけると ECE 0.012〜0.02。
**確率がしきい値として使える**ようになったことが、Decision Model の一番の実用的価値でした。

### (d) 1 つの小さな層で 6 種類の仕事をこなせた

二択 (Noul)、多択 (Choice)、段階評価 (Score)、英語と日本語、選択肢がサンプルごとに変わるツール選択。
これらを全部混ぜて **262 万パラメータの層 1 つ**に学習させても、個別に学習した場合とほぼ同じ精度でした。

| タスク | 個別学習 | 6 タスク共有 |
|---|---|---|
| 意図分類 英語 (18 択) | 90.6% | 91.1% |
| 意図分類 日本語 (18 択) | 89.8% | 90.0% |
| 意図分類 英語 (60 択) | 86.8% | 86.6% |
| 不快ツイート判定 (二択) | 81.6% | 80.6% |
| レビュー星予測 (5 段階) | 67.3% | 65.4% |
| ツール選択 (可変選択肢) | 95.2% | 94.4% |

「選択肢の説明文を読んで、状態との相性を点数にする」という作りにしたおかげで、
選択肢の数も種類も違うタスクが 1 つの層に同居できました。

## 5. TypeSafe の事前の期待に対して、プラスとマイナス

仕様書に書かれていた仮説を 1 つずつ判定します。**外れたものの方が学びが大きい**ので、そこを厚く書きます。

### ❌ 外れ (1): 「文章生成をやめれば大幅に速くなる」

仕様書の H1 は「LM head と逐次生成を外せば大幅高速化」でした。**速度に関しては、ほぼ外れです。**

理由は単純で、LLM 側も「選択肢の文字に強制して、1 トークンだけ出させる」設定にすれば、
それはもう**逐次生成ではなく 1 回の forward** だからです。実測で 4B の LLM が 14.5 ms、
同じ 4B の Decision Model が 15 ms。**ほぼ同じ**でした。

ではどこから速さが来るのか。実験で分離できた要因はこの 3 つです。

1. **モデルを小さくできること** (0.6B なら 10 ms)。そしてこれは (a) の結果、精度を落とさずにできる
2. **複数質問を 1 回の forward にまとめられること** (8 問 508 ms → 23 ms)
3. **JSON を生成させないこと** (LLM に JSON で答えさせると 1 問でも 65 ms、16 問で 895 ms)

つまり**売り文句を「生成をやめたから速い」ではなく「小さいモデルで済み、質問をまとめられ、JSON を作らない」に置き換えるべき**、
というのが今回一番はっきりした設計上の学びです。

### ❌ 外れ (2): 「大きい LLM の確率を蒸留した方が精度も校正も良くなる」

仕様書の H3 は「hard label より soft label」でした。**今回の設定では逆効果**です。

| 学習に使った正解 | 正答率 |
|---|---|
| 人手の正解ラベル (hard label) | **90.6%** |
| 27B 先生の確率分布 (soft label) | 86.1% |
| 両者の平均 | 89.4% |
| 4B と 27B の分布を平均した先生 | 84.7% |

理由は身も蓋もなくて、**先生 (ゼロショット 27B、正答率 87.4%) が正解データより弱いから**です。
蒸留すると先生の間違いまで忠実に覚えます (先生との KL 距離は 0.455 → 0.112 に下がるので、蒸留自体は成功している。
成功した結果として弱くなる)。

**教訓**: 蒸留が効くのは「人手の正解が存在せず、LLM だけが答えを持っている」領域だけ。
正解データがあるなら素直にそれで学習するのが一番強い。TypeSafe が蒸留を軸にしているとすれば、
それは彼らが**正解データを持たない多様な質問**を扱っているからだと推測できます。

### ❌ 外れ (3): 「確信度が低いときは LLM にフォールバックすればいい」

仕様書 §11 と §19 の中心的な構成です。実際に測ってみました
(Decision Model が答え、確信度がしきい値未満の質問だけ 27B に回す)。

| しきい値 | LLM に回った割合 | 最終正答率 |
|---|---|---|
| 0 (DM 単独) | 0% | **91.6%** |
| 0.6 | 8% | 91.6% |
| 0.8 | 15% | 91.0% |
| 0.9 | 20% | 90.6% |
| 1.0 (LLM 単独) | 100% | 87.5% |

**フォールバックするほど精度が下がりました。** 当たり前といえば当たり前で、
このタスクでは Decision Model の方が 27B より強いので、難しい問題を弱い方に回していることになります。

これは「System 1 が速くて安い / System 2 が遅くて賢い」という前提そのものが、
**専用学習をした瞬間に崩れる**ことを意味します。フォールバック先が本当に強い場合 (未知のドメイン、
学習データにない質問) にだけ有効な設計です。

代わりに意味があったのは、**同じ確信度を「自動実行するかどうか」に使う**運用でした。

| | カバー率 | その範囲の正答率 |
|---|---|---|
| Decision Model 確信度 ≥ 0.9 | 79.8% | **98.2%** |
| 27B LLM 確信度 ≥ 0.9 | 84.2% | 95.4% |

「8 割を 98% の精度で自動処理し、残り 2 割を人間に回す」が成立します。
27B は同じしきい値で 95.4% しか出ないので、**確率の質がそのまま自動化率の差になる**わけです。

### ⭕ 当たり: 状態の共有・JSON 構文エラーゼロ・確率の校正

- **状態の共有**: 8 質問で単問の 1.5 倍、16 質問で 2 倍。仕様書の成功基準 (8 質問で 2 倍未満) を達成
- **構文エラー**: 出力が確率ベクトルなので原理的にゼロ。仕様書 v0 の基準を構造的に満たす
- **校正**: 温度補正 1 パラメータで ECE 0.02 前後。仕様書 v3 の基準 (0.05 以下) を達成

校正については副次的な発見があって、**損失関数を工夫するより温度補正の方がずっと効きます**。
KL / CE / Focal / Brier との複合を 8 通り試しましたが、補正後の ECE はどれも 0.02 前後に収束しました。
(なお Brier を単独で使うと学習がまったく進みません。初期状態で softmax が飽和していると勾配が消えるためです。
仕様書は Brier を候補に挙げていますが、単独では使えないので複合前提です。)

### ⭕ 想定以上: 必要なモデルサイズ

仕様書は 3B〜8B を想定していましたが、**0.6B でゼロショット 27B を超えました**。
用途が固定なら 0.6B で足ります。これは「エッジ GPU に置く」「1 台で大量に捌く」という商用シナリオに直結する誤算です。

### ⚠️ まだ遠い: 「汎用 Decision Model」として独立させる

6 タスク混合の層は、**学習した種類の質問**には強い。しかし API のデモで学習データにない質問を投げると崩れます。

```
状態: 「商品がまだ届いていません。3日前に発送済みと表示されています。」(premium 顧客)

Decision Model:  部署=配送(100%)  緊急対応が必要=3%   深刻度=0.30
27B LLM:         部署=配送(100%)  緊急対応が必要=100%  深刻度=2.0
```

部署の判定 (学習済みのタスク型) は一致しますが、「緊急か」という**一度も学習していない二値質問**では
真逆の答えを出しています。Decision Model 側は「見たことのない質問には、とりあえず No と答える」状態です。

つまり **TypeSafe の本当の資産は、アーキテクチャではなく「膨大で多様な質問の学習データ」**である可能性が高い。
アーキテクチャは今回 1 日で再現できましたが、こちらは 1 万件 × 6 種類では全く届きませんでした。

## 6. 結局、どう使うのが現実的か

**業務が固定なら今すぐ使えます。** 自社の問い合わせ分類やルーティングのように質問と選択肢が決まっているなら、
正解付きデータ 1 万件と 0.6B〜4B のモデルで、ゼロショット LLM より正確で・確率が信頼できて・十分速い判定器が数分で作れます。
特に「8 割を 98% 精度で自動処理」ができるので、投資対効果は分かりやすい。

**汎用にしたいなら、次にやるべきはアーキテクチャではなくデータです。** 多様な質問を LLM に大量生成させて学習させる
(仕様書 Phase 2 の本格化)。ただし蒸留は「LLM が正解を知っている領域」に限ること。

**フォールバック設計は再考が要ります。** 「確信度が低いから LLM へ」は、LLM の方が強いときにしか成立しません。
専用学習済みモデルの方が強い領域では、「確信度が低いから人間へ」または「確信度が高いものだけ自動実行」が正解です。

## 7. 用語ミニ辞典

| 用語 | 意味 |
|---|---|
| backbone | 文章を読んで意味ベクトルにする本体 (Transformer)。今回は Qwen をそのまま使い、基本は凍結 (学習しない) |
| head | モデル最後の小さな出力層。文章用の LM head を外し、選択肢の点数を出す層に替えた |
| 凍結 (freeze) | 本体のパラメータを更新しないこと。ベクトルを 1 回計算してキャッシュすれば、以後の学習が数秒で終わる |
| LoRA | 本体に小さな差分行列だけ足して学習する省メモリな追加学習。今回は 20 分で +1.7pt |
| hard label / soft label | 「正解は 3 番」だけを教えるか、「3 番 72%, 1 番 21%…」という分布を教えるか |
| 蒸留 (distillation) | 大きい先生モデルの分布を正解として小さい生徒に教えること |
| ECE | 確率の信頼性。「自信 90% と言ったものが本当に 90% 当たるか」のズレ。0.05 以下が実用目安 |
| Brier score | 確率の二乗誤差。精度と校正をまとめて見る指標 |
| 温度補正 | 出力の自信を一律に強める/弱める 1 パラメータの校正。安くてよく効く |
| KV cache | 読み込み済みの文の中間結果。使い回すと同じ文を再計算せずに済む |
| block-diagonal attention | 「質問同士は互いを見ない」よう注意の範囲を区切る仕掛け。複数質問を 1 回の forward で処理できる |
| vLLM / guided choice | LLM の高速推論サーバーと、出力を選択肢の文字列に強制する機能。今回の LLM 側の武器 |
